# Security policy

Please report suspected vulnerabilities privately to
[cagatayuresin@gmail.com](mailto:cagatayuresin@gmail.com). Include the affected
version, a minimal reproduction, and the expected impact. Do not include real
credentials or customer data, or open a public issue containing an exploit
before the maintainer has had a chance to investigate.

Security fixes target the current source and the next release. Older releases
do not have a separate maintenance branch. Use a maintained Python version
with current security updates.

## Connection and data handling

- HTTPS with certificate and hostname verification is the default. HTTP requires
  an explicit `secured=False` and is intended for trusted local development.
- Each connection has a finite timeout (30 seconds by default). This is a socket
  timeout, not a total deadline for the entire operation.
- XML response parsing rejects DTDs, entities, and external references. Responses
  are limited to 30 MiB after decompression; paginate large reads.
- HTTP error bodies are discarded without being read. Requests are not retried
  automatically after a disconnect, preventing an ambiguous write from being
  replayed by the transport.
- Supply host settings from trusted configuration. URL validation is not an SSRF
  allowlist: do not let an untrusted user choose an arbitrary destination.
- Use an Odoo account or API key with only the permissions your integration needs.
  Store secrets outside source control. Authentication errors generated by this
  wrapper do not include credentials. Remote faults may contain server-provided
  details; review them before logging or sharing.
- `Bot` keeps a mutable active model and persistent connections. Use a separate
  instance per thread, and close it explicitly or with a context manager.

## Automated checks

GitHub Actions runs offline regression tests, Ruff, Bandit, pip-audit, zizmor,
package validation, and Trivy on pushes, pull requests, manual runs, and a weekly
schedule. Trivy scans dependencies, secrets, and supported infrastructure
configuration, and fails on HIGH or CRITICAL findings. pip-audit fails on any
known vulnerability returned by its database. No vulnerability ignore list or
`continue-on-error` bypass is configured for these checks.

The dependency lock files include runtime and development tools. Their hashes
verify downloaded package artifacts; they do not prove a package is safe.
Scans reflect the available advisory databases at scan time. Follow the commands
in [README.md](README.md#development-and-checks) to reproduce them.
